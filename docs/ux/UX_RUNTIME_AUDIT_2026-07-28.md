## Критические находки и исправления

### 1. Решение планировщика терялось перед запуском

Планировщик мог выбрать свободный Codex, но очередь запуска повторно выбирала
исполнителя из поля задачи. Обычный `executor` фактически становился постоянным
пином, поэтому Claude загружался, а свободные агенты простаивали.

Исправлено:

- разрешённые агенты проекта стали пулом авторизации;
- обычный исполнитель задачи стал предпочтением, а не жёстким пином;
- явный `executor_pinned` сохраняет строгий выбор пользователя;
- выбранный планировщиком агент передаётся до самого запуска;
- неудачный исполнитель исключается из следующей попытки;
- загрузка считается по сохранённому `provider_id`, а не приписывается Claude.

### 2. Счётчики использовали разные определения

Верхняя строка считала только кратковременные состояния run, а раздел
«Ожидают запуска» дополнительно показывал устойчивую очередь. Поэтому верх мог
показывать `0`, когда внизу было `9`.

Исправлено:

- добавлена единая модель `ExecutionCounts`;
- верхняя строка, глобальная полоса и секции Live Execution Center используют
  одну классификацию;
- очередь учитывается в `Ожидают запуска`;
- старые неудачные попытки скрываются из внимания, если новая попытка уже
  выполняется или задача завершена;
- скрытые оператором карточки исключаются из видимого счётчика.

### 3. Процент выполнения был сохранённой плановой цифрой

Kanban мог продолжать показывать старое поле `progress`, хотя реальный run уже
сменил состояние.

Исправлено: для текущего run процент и стадия вычисляются из фактического
жизненного цикла, времени выполнения, timeout/оценки и результата completion.
Это актуальный операционный индикатор, но не телеметрия внутренних шагов модели:
провайдеры пока не отдают точный процент исполнения промпта.

### 4. Автодоработка не покрывала реальные красные исходы

Повторная доработка не запускалась для части состояний validation/review/merge.

Исправлено: повторная попытка поддерживает `VALIDATION_FAILED`,
`REVIEW_REJECTED` и `MERGE_BLOCKED` при падающих проверках, с ограничением числа
попыток и исключением уже неудачных исполнителей.

### 5. Ручной и автоматический merge не имели единого последовательного шлюза

При выключенном auto-merge не было ясного действия на завершённой задаче, а
разные процессы могли одновременно войти в merge.

Исправлено:

- на допустимой завершённой задаче появляется «Сделать merge»;
- ручной и автоматический пути используют один completion service;
- межпроцессный file lock допускает только один merge одновременно;
- занятый слот откладывает следующую задачу без расходования retry;
- проверка CI остаётся обязательным барьером.

## UX-находки и исправления

### Навигация

Из 21 обработчика страниц оставлено 10 ежедневных пунктов:

- Обзор, Kanban, Live Execution Center, Проекты, Git Center;
- Волны, Создать задачу;
- Журнал запусков, AI-агенты, Портфель.

Содержимое объединено:

- аналитика, репозитории и артефакты — в главную;
- таймлайн — в журнал запусков;
- обзор и исполнение — в Портфель;
- задания, отчёты, контекст, настройки, чат, аудит и roadmap — внутри Проектов;
- рекомендации — в сворачиваемый блок Kanban;
- очередь и её запуск — только в Live Execution Center.

Старые адреса скрытых страниц сохранены для существующих закладок. Командная
палитра показывает только ежедневные назначения и действия создания задачи.

### Клики и ссылки

Исправлено:

- верхняя кнопка поиска теперь открывает реальную командную палитру вместо
  неработающего placeholder;
- закрытая палитра больше не появляется снова после навигации;
- карточки обзора проектов имеют явную кнопку открытия;
- заголовки получили стабильные page-specific anchors и не наследуют ссылку
  предыдущего экрана;
- ручной запуск очереди перенесён вместе с самой очередью в Execution Center.

### Мигание и лишняя работа

Причины: CSS-анимация прозрачности fragment, полный polling каждые 3–5 секунд,
spinner на refresh и двойной rerun кнопки обновления.

Исправлено:

- удалена анимация прозрачности;
- мониторинг выключен по умолчанию;
- интервалы полного мониторинга: 15/30/60 секунд;
- компактная глобальная строка обновляется отдельно раз в 15 секунд;
- ручное обновление делает один проход;
- тяжёлые разделы Dashboard и Portfolio вычисляются только после выбора, а не
  скрыто во всех вкладках.

## Фактический блокирующий статус production

Текущий production на `ab67f8c` имеет:

- `enabled=false`;
- `auto_launch=false`;
- `auto_merge_after_checks=false`;
- `auto_rework=false`;
- `max_global_concurrency=1`;
- `max_agent_concurrency=1`;
- `max_rework_attempts=0`.

Поэтому текущий запущенный экземпляр не может автоматически распределять,
дорабатывать и сливать задачи. Включать эти флаги до доставки исправленного
кода нельзя: это активировало бы старый путь запуска.

## Roadmap ввода

### Этап 0 — доставка

1. Просмотреть diff ветки и создать отдельный commit.
2. Влить ветку в production-код.
3. Перезапустить UI и daemon.
4. Выполнить smoke-проверку на копии/контрольной задаче.

### Этап 1 — безопасная автоматизация

1. Включить pipeline и auto-launch.
2. Установить `max_global_concurrency=2`, `max_agent_concurrency=1`.
3. Включить auto-rework с `max_rework_attempts=2`.
4. Оставить auto-merge выключенным; проверить ручную последовательную очередь.

### Этап 2 — наблюдение

В течение полного рабочего цикла проверить распределение по провайдерам,
отсутствие двойных запусков, совпадение четырёх счётчиков, terminal persistence,
повторную доработку и освобождение merge lock.

### Этап 3 — auto-merge по явному решению

Включать только после этапа 2, сохраняя обязательные CI/review gates и
единственный последовательный merge slot.

## Оставшийся технический долг

- Большой `app.py` всё ещё содержит обработчики старых deep-link страниц; их
  физическое удаление требует отдельной миграции закладок.
- Внутренняя страница одного проекта использует Streamlit tabs, которые
  вычисляют скрытые вкладки; следующий безопасный шаг — ленивый segmented
  selector без изменения контрактов форм.
- Точный процент внутренних шагов агента невозможен без progress events от
  провайдера; текущий процент честно отражает lifecycle/time estimate.
- Файловый Portfolio roadmap и оперативный task store остаются разными
  источниками. Интерфейс теперь явно подписывает их, но объединение хранилищ —
  отдельная миграция данных.
