## 1. Executive Summary

AI Command Center — работающий, ежедневно пригодный к использованию Streamlit-инструмент для одного founder-пользователя, с реально сильными местами (защита от shell-инъекций, движок SQLite runtime v2 с WAL/CAS/транзакциями, тестами на реальной многопоточности/мультипроцессности для Portfolio-блокировок) и реально серьёзными пробелами (небезопасный сетевой bind по умолчанию, отсутствие блокировок при записи `tasks.json`/`execution_queue.json`, отсутствие единой модели задачи, отсутствие настоящего импорта задач, отсутствие автосоздания worktree в основном сценарии запуска).

Тестовый прогон: **910/910 pytest пройдено**, `ruff check` — чисто, `compileall` — без ошибок синтаксиса, `mypy` не настроен. Это подтверждает, что заявленный функционал в основном действительно работает так, как описан в тестах — но тесты не покрывают ряд критичных для founder-сценариев путей (конкурентная запись `tasks.json`, sетевой bind, единая модель задачи, batch-импорт), что и стало предметом этого аудита.

Продукт **не является ни "просто прототипом", ни "production-ready без оговорок"**. Он находится между этими полюсами: ядро (Kanban, запуск агента, Execution Center, Portfolio, отчёты) реально работает и неплохо протестировано; периферия (импорт задач, desktop UI, единая модель задачи, сетевая безопасность, конкурентность JSON-хранилища) требует укрепления до того, как можно масштабировать использование за пределы одного founder на одной машине.

## 5. Матрица всего функционала (по подсистемам)

### 5.1 Создание/импорт задач и модель Task

- **Единой канонической модели Task нет.** Форма собирается из трёх фабрик (`tasks_repository.new_task_record`, `models.default_task_workflow_fields`, `models.default_task_execution_fields`) плюс `normalize_task` докладывает поля только при чтении. Плюс отдельная, несовместимая `PortfolioTask` (`portfolio_models.py:79-181`) — четвёртая форма.
- Боевой `data/tasks.json` (9 записей) **не соответствует** ни коду, ни реестру: ручные строковые ID вида `AICC-AUDIT-001`, отсутствуют `created_at`/`updated_at`, есть посторонние поля `source`/`target_version`/`parallel_group`, значения `project` (`"AI Command Center"`, `"AIOS Product"`, `"Ecosystem"`) не входят в `models.PROJECT_IDS`. Совпадающие по содержимому файлы найдены в незалогиненном в код каталоге `data/_founder_reset_backup/task_import_2026-07-21_03-29-41/` — то есть **боевые данные попали в файл вручную/скриптом снаружи приложения**, а не через изученный код. **(Finding B-1, Blocker)**
- Пути создания задачи — только по одной штуке за раз: ручная форма (`app.py:2067`, требует успешного выполнения `scripts/start-task.sh`), «Создать следующую задачу» из завершённого run (`app.py:760`), чат → «Сделать задачей» (`app.py:2294`), Portfolio-карточки (отдельное read-only хранилище, никогда не пишет в `tasks.json`).
- **Batch-импорт JSON/TXT/Markdown, пакеты от ChatGPT, множественное создание за один раз — в коде не существуют** ни в каком виде (UI/CLI/API).
- `scripts/start-task.sh` поддерживает только `AIOS`/`BANK`/`LEGAL` (жёсткий `case`), тогда как реестр включает 6 проектов — форма «Создать задачу» **молча проваливается** для AICOS/BUSINESS/PERSONAL, хотя остальные пути создания это ограничение не наследуют. **(Finding A-3, Major)**
- Статусы Kanban (`Backlog → Next → In Progress → Review → Done`) — обычный `st.selectbox`, переход в любую сторону разрешён кодом, ограничение только конвенцией порядка в выпадающем списке.
- **Нет проверки уникальности ID.** `uuid4().hex` генерируется всегда, но ничто не проверяет коллизии. Последствия подтверждены по коду: `tasks_by_id = {t["id"]: t for t in tasks}` молча схлопывает дубликаты; `update_task_status` обновляет только первое совпадение; **`delete_task` удаляет ВСЕ записи с совпавшим ID** — один клик "Удалить" по одной карточке может стереть несколько задач разом, если дубликат когда-либо возникнет. **(Finding B-2, Blocker)**
- `tasks_repository.save_tasks` атомарна (temp-файл + `os.replace`), но **без `fsync`** и **без блокировки** — в отличие от `storage.atomic_write_json`, которую дублирует и ослабляет. Два одновременных Streamlit-сеанса, сохраняющих разные задачи, могут потерять изменения друг друга (lost update). **(Finding B-3 / часть общего Reliability-финдинга ниже, Blocker)**
- Резервного копирования/rollback в приложении нет; `data/_founder_reset_backup/` — не продукт кода.
- Битые/повреждённые данные: `load_tasks` при ошибке парсинга молча возвращает `[]` без сообщения пользователю — риск, что следующий `save_tasks` перезапишет повреждённый, но восстановимый файл пустым списком.
- Обнаружения циклов зависимостей нет; ближайшая логика (`project_intelligence._longest_blocked_chain`) сама документирована как «не cycle-safe», защищена только ограничением глубины 25.

### 5.2 Проекты и реестр

- Канонический реестр — `models.PROJECT_IDS = [AIOS, AICOS, BANK, LEGAL, BUSINESS, PERSONAL]`, единственный, тестами защищён от повторения исторического бага (когда локальный `PROJECTS`-словарь в `app.py` молча терял AICOS).
- Все проверенные UI-селекторы (`project_selector.py`, Kanban-фильтры и т.д.) сегодня действительно перебирают полный `PROJECT_IDS` — повторного случая "проект виден только в режиме «Все проекты»" в коде не найдено.
- **Но практический эквивалент этой проблемы жив**: `data/project_config.json` содержит `repository_path` только для AIOS; у остальных пяти проектов эти данные пусты → все репо-зависимые виджеты (worktree-список, git health, Portfolio-launcher) для них показывают "не настроено", что снаружи неотличимо от "проект не виден".
- Отдельный, специально несвязанный неймспейс проектов существует в `portfolio_config.py` (`AICC`, `PRODUCT`, `INFRA`, плюс переиспользованные строки `AIOS`/`AICOS`) — по дизайну не совпадает с `models.PROJECT_IDS`, но легко перепутать.
- `AICOS.md` числится в `PROJECT_STATUS_FILES`, но физически отсутствует в `projects/` — обрабатывается корректно ("файла ещё нет"), не падает.

### 5.3 Запуск Claude Code / AI Agents

- Бинарник `claude` резолвится только через `PATH` (`shutil.which`), pre-flight-проверка существует, но подключена только к чат-фиче, **не к основному лаунчеру задач** — можно пройти весь confirmation-флоу и получить отказ только в момент реального запуска. **(Finding A-4, Minor)**
- Subprocess — **везде** `argv`-список, `shell=False`, промпт одним элементом argv; закреплено именованными регрессионными тестами (в т.ч. с промптом, содержащим `; rm -rf / ; $(whoami)`). Это одна из сильных сторон системы.
- Существуют **два параллельных стека запуска**: legacy-синхронный (`agent_runner.run_claude_code`/`execute_agent_launch`, без отмены, без реконсиляции) и v2-асинхронный (`runtime/supervisor.py`/`execute_agent_launch_v2`, с PID-трекингом, отменой, вотчдогом таймаута с SIGTERM→SIGKILL по process group, реконсиляцией зависших run по PID+identity). **Сегодня основной UI (`render_agent_launcher`) использует исключительно v2** — legacy-путь жив в коде и тестах, но не вызывается ни из одного реального UI-сценария. Само существование двух путей, пишущих в одни и те же поля задачи, — риск (см. §5.4). **(Finding A-5, Major, спящий)**
- Подтверждение перед запуском реально навязывается **на бэкенде**, не только в UI (`context_service.require_launch_confirmation` вызывается изнутри `Supervisor.start_raw`/`cancel`, а не только из чекбокса). Это хорошо.
- **Но**: расхождение ветки, «грязное» дерево, detached HEAD — это только предупреждения, снимаемые одним чекбоксом «подтверждаю несмотря на предупреждения»; несуществование/невалидность workspace — единственные жёсткие блокеры. **(Finding A-6, Major)**
- Параллельный запуск: SQLite (`enforce_workspace_lock=True`) корректно не даёт запустить два run на **один и тот же** путь/задачу одновременно. Но основной Kanban-лаунчер **не создаёт worktree сам** — параллельная безопасность полностью зависит от того, что founder заранее вручную указал разные `workspace_path`. Это прямое подтверждение подозрения из задания. **(Finding A-2, Major)**

### 5.4 Git и worktree

- `git_info.py` — полностью read-only, безопасен; **ahead/behind не вычисляется вообще** (не "устарело", а отсутствует как функция), `git fetch` нигде не вызывается.
- Реальное создание/удаление worktree в продукте **существует, но только внутри `portfolio_launch.py`** (Portfolio auto-launch): `git worktree add -b <branch> <path> <base>`, с валидацией `task_id` по regex, с проверкой контейнмента пути (`_assert_within_root`, резолвит симлинки), с откатом (`remove_worktree`/`delete_branch`, best-effort) только для того, что создал сам запуск — существующие worktree никогда не трогаются (протестировано отдельно).
- Явной защиты от операций над `main` нет — есть только косвенная защита за счёт того, что `git worktree add` откажет, если `main` уже открыт в основном рабочем дереве. **(Finding A-7, Major)**
- Git Center и Workspace Launcher — стопроцентно витрина, ни одной мутирующей кнопки; ни одна подпись кнопки в `app.py`, связанная с git, не обещает действие, которого нет за кадром (кроме честной кнопки запуска Portfolio).
- `commit`/`push`/`merge` продукт не вызывает никогда — только текстово запрещает это агенту в промпте (не в коде, не enforced).
- `os_actions.py` (Reveal in Finder, Open Terminal, Copy to clipboard) — безопасен: только macOS, только фиксированный argv, никогда не печатает и не выполняет команды внутри открытого Terminal.

### 5.5 Execution Queue

- `data/execution_queue.json`, реально подключена к UI (кнопки «Запустить готовые» / «Запустить следующую»), реально читает/пишет очередь при добавлении задач с Kanban.
- Осознанный дизайн «нет скрытого планировщика» — ничего не запускается автономно, только по клику человека.
- Готовность/блокировку вычисляет через `models.unmet_dependencies`; удалённая/уже `Done`-задача автоматически отменяет свою запись в очереди.
- **Блокировок при записи нет** — тот же класс риска, что и у `tasks.json`: два одновременных клика «Launch Ready» в разных вкладках могут прочитать одно и то же состояние до того, как любой из них запишет.

### 5.6 Portfolio Execution

- Настоящая гонка двойного запуска **устранена корректно**: exclusive-create claim-lock на задачу + `fcntl.flock` на реестре с повторной проверкой под локом. Подтверждено тестами на реальных потоках (`threading.Barrier`) **и** реальных отдельных процессах (`multiprocessing`), включая негативный контрольный тест, воспроизводящий сам баг на незащищённом паттерне.
- **Уточнение к заданию**: коммит `b29f3f5` ("Fix Portfolio duplicate launch status", PR #8, самый свежий на `main`) — это **фикс UI-статуса**, не гонки данных; настоящий фикс блокировки был раньше, в неупомянутом в задании коммите `2de7dd2`. Коммиты `70fb00b`/`20e9f95` (PR #7) действительно устранили баг парсинга flow-list (незакавыченные элементы `[A, B]` молча парсились в `[]`, обходя проверку зависимостей) — заменой fail-open regex на fail-closed токенайзер.
- **Новый, не покрытый тестами баг найден и подтверждён прямым выполнением**: незакавыченный завершающий `#`-комментарий в скалярном значении (`status: ready # note`) молча становится частью значения, а не отбрасывается/отклоняется — нарушает собственный принцип модуля «fail closed». **(Finding B-4, Minor)**
- Claim-lock **не восстанавливается автоматически** после аварийного завершения процесса между claim и release (`kill -9`, падение хоста) — задача остаётся заблокированной навсегда до ручного удаления файла оператором. Задокументированный осознанный компромисс, но реальная эксплуатационная проблема. **(Finding A-8, Major)**
- Повторный запуск **не идемпотентен** после успешной регистрации — кнопка Launch блокируется навсегда для этого `task_id`, даже если сам run потом упал/был прерван; единственный способ разблокировать — вручную отредактировать `data/portfolio_launches.json`.
- Portfolio-задачи — полностью отдельное хранилище (внешние Markdown-карточки), никогда не пишутся в `tasks.json`, поэтому расхождения с Kanban структурно невозможны — но и обратной синхронизации тоже нет.

### 5.7 Runtime v2 и SQLite

- Схема (`schema_version=3`): таблицы `task`, `session`, `run`, `run_event`, `report`, `schema_version`. **В боевом окружении все пять таблиц данных пусты (0 строк)** — либо v2 никогда реально не использовался в этой среде, либо был сброшен (рядом лежит `data/_founder_reset_backup/`).
- Инженерно — лучшая часть кодовой базы: `journal_mode=WAL`, `busy_timeout=30000`, `BEGIN IMMEDIATE`-транзакции, foreign keys on, optimistic concurrency через колонку `version` (`LostUpdateError` при рассинхроне), проверка "workspace уже занят" — внутри той же транзакции, что и `INSERT`. Подтверждено тестами на **реальной** многопроцессности (`multiprocessing.get_context("spawn")` + барьер).
- `legacy_import.py` — полностью реализован, идемпотентен (проверено тестом на двойной запуск), **но нигде не вызывается из приложения** — мёртвый инструмент миграции. **(Finding B-5, Minor)**
- `task_sync.py` — однонаправленная синхронизация `run → task`, но **не фоновая**: срабатывает только пока открыта страница Live Execution Center (Streamlit-фрагменты с интервалом 2–5с) плюс один раз при старте процесса. Если никто не смотрит на эту страницу, поля задачи (`launch_status`, `report_path`, `latest_verdict`) не обновятся до следующего открытия страницы. **(Finding A-9, Major)**
- **Источник истины**: для Run/execution-state — однозначно `runtime.db` (по коду и комментариям, и структурно верно сегодня). Для Task (Kanban-запись) — однозначно `data/tasks.json`. Узкая зона полей-пересечения (`current_run_id`, `launch_status`, `report_path`, `branch`, `last_run_at`, `latest_verdict`, `pull_request_url`) может писаться **двумя** независимыми путями (legacy sync + v2 sync) без общей блокировки — сегодня безопасно только потому, что legacy-путь не вызывается из живого UI, не потому что это где-то enforced в коде. **(Часть Finding A-5)**

### 5.8 Desktop-архитектура

- Кода — ноль: ни одного файла с `PySide6`/`pyqt`/`QtWidgets`/`QApplication` во всём репозитории (вне `.venv`).
- Документация (`docs/desktop/*`, 10 файлов) последовательно и честно помечена "D0 — только документация, кода ещё нет" в каждом файле; ни в одном месте не найдено завышения статуса (никакой D1–D4-функционал не заявлен как готовый). Корневые `README.md`/`CHANGELOG.md`/`ARCHITECTURE.md` синхронно ссылаются на этот же статус.
- Ни одного из D0-инвариантов не реализовано и не протестировано (см. таблицу §9 ниже) — все "Specified only" или "Not Started".

## 13. Critical path

1. **BLOCKER-1** (сетевой bind) — тривиальная по объёму работы, максимальная по риску правка; делать первой и отдельно от всего остального.
